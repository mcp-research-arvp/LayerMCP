Overall issue
The evaluator assumes:
workflow final answer = last executed tool result
It then applies one broadly scalar-oriented matcher:
formatted_final_scalar_v1
The seven multi-step datasets actually have three different answer contracts:
1. No workflow-final-answer gold.
2. Structured final-tool-result gold.
3. User-facing textual or formatted numerical gold.
One matcher cannot correctly evaluate all three.

Mathematics
Mathematics stores both expected and executed answers as structured objects.
Expected: structured object
Actual: structured object
Matcher: attempts scalar extraction
Result: extraction error or mismatch
Even identical objects are marked incorrect.
For calculator rows, the evaluator extracts the numerical result, then compares that number against the complete expected object:
Expected: {"expression": "6 + 10", "result": 16}
Extracted actual: 16
Result: mismatch
Mathematics fix
Use the existing recursive structured matcher:
recursive_json_subset_v1
against the complete final tool result.
No inference rerun is needed. All six completed Mathematics model conditions can be rescored from their saved artifacts.
FinQA and ConvFinQA
These datasets expect user-facing answer strings such as:
"11%"
"10.83%"
"$218,612"
"yes"
The evaluator extracts a numerical tool result and formats it for comparison. The percentage logic is defective because it always multiplies by 100 when the expected answer ends in %.
But both conventions exist:
Tool result 0.10745  → expected "11%"
Tool result 10.8262  → expected "10.83%"
The first requires multiplication by 100. The second is already expressed as a percentage and must not be multiplied.
Therefore, some apparent failures are matcher errors while others are genuine incorrect model results. The current published accuracies mix the two and cannot distinguish them reliably.
Finance display-answer fix
Create separate FinQA and ConvFinQA matchers supporting:
- explicit ratio versus already-scaled percentage representation;
- benchmark-defined rounding;
- commas and currency markers;
- negative values;
- yes/no answers;
- legitimate prose answers;
- query-table scalar extraction;
- empty gold and null results.
The matcher must determine scaling from an explicit benchmark contract or operation metadata. It should not simply try both x and x × 100, because accepting whichever matches could create false positives.
Saved-artifact rescoring is sufficient. No new inference is needed for FinQA or ConvFinQA.
FinRetrieval
FinRetrieval has a different problem.
Expected:
"In fiscal year 2023, the company reported ... -12,393,820 thousand Turkish lira."
Executed result:
{
  "fundamentals": [
    {
      "value_year_to_date": -12393820.0,
      "unit": "Thousand",
      "calendar_period": "2023FY",
      "id": 110327432
    }
  ]
}
The retrieved evidence may contain exactly the necessary fact, but a natural-language sentence cannot equal a retrieval dictionary.
More importantly, the evaluator never asks the model to produce a final answer after completing the tool sequence. It only saves the last tool result. Therefore, there is no model-generated final response available to score against the natural-language gold answer.
This is a protocol mismatch—not merely a formatting bug.
FinRetrieval options
Option A: retain the current guided tool-execution protocol
- Do not report workflow-final-answer accuracy.
- Report tool selection, arguments, execution, semantic step results and retrieval-evidence accuracy.
- Mark workflow-final-answer accuracy as unavailable.
- Keep all current saved runs; no inference rerun is needed.
Option B: evaluate final natural-language answering
- Add an explicit post-tool model call.
- Give the model the executed workflow context.
- Save its final response separately.
- Compare that response with the natural-language gold using an appropriate grounded-answer matcher.
- Assign a new evaluation-protocol version.
- Rerun every FinRetrieval model condition.
For completing the current LayerMCP baseline, Option A is cleaner. The current experiment measures guided predicted tool execution; adding answer synthesis now would introduce a materially different evaluation stage.
The existing Gemma reasoning FinRetrieval run remains useful:
Tool selection per step: 99.53%
Correct arguments per step: 99.26%
Correct results per step: 99.26%
All step results correct: 97.94%
Its reported 0% workflow-final-answer accuracy is invalid and should be suppressed.
Where the defect originates
The central fault is in the workflow-final scoring path in evaluation/evaluate.py:
1. The evaluator finishes the workflow.
2. It takes the last step’s tool_result_value.
3. It treats that value as the workflow’s final answer.
4. It applies formatted_final_scalar_v1.
5. It counts every non-empty expected value as successfully scored.
6. It publishes an accuracy even when the expected and actual representations are incompatible.
There is no benchmark-family or answer-contract dispatch.
Required code changes
Implement explicit workflow-final-answer contracts:
No gold
→ unscored; accuracy null

Structured gold
→ recursive structured matcher

FinQA/ConvFinQA display gold
→ dataset-specific display-answer matcher

FinRetrieval prose gold without saved model response
→ unscored
The evaluator should record:
- matcher ID;
- contract ID;
- whether scoring was supported;
- correct, mismatch and extraction-error counts;
- gold count separately from valid scored count.
An unsupported contract must produce:
workflow_final_answer_accuracy: null
workflow_final_answer_scored: 0
not a false 0% accuracy.
Metrics to suppress temporarily
Suppress workflow-final-answer metrics for:
- finance_convfinqa
- finance_finqa
- finance_finretrieval_replay
- math_controlled
The first, second and fourth can later be recovered through saved-artifact rescoring. FinRetrieval remains unscored unless a final-response generation stage is introduced.
Do not suppress:
- step tool selection;
- exact argument diagnostics;
- execution success;
- step semantic result accuracy;
- complete tool-sequence accuracy;
- complete semantic-output-sequence accuracy;
- latency and execution-error counts;
- model, prompt, registry and reasoning provenance.
The three no-gold groups should continue showing workflow-final accuracy as unavailable rather than zero.
Effect on existing reports
This defect affects multi-step workflow-final-answer reporting only.
It does not invalidate:
- the single-step tables;
- multi-step tool-selection results;
- multi-step argument metrics;
- multi-step execution and semantic step-result metrics.
Any overall multi-step table that aggregates workflow-final-answer accuracy across all seven dataset groups must be withdrawn or regenerated after the fix. Not every dataset even defines the same final-answer metric.
Recommended implementation order
1. Add benchmark-family/contract dispatch.
2. Fix structured Mathematics matching.
3. Fix FinQA and ConvFinQA display matching.
4. Mark FinRetrieval final-answer scoring unsupported under the current protocol.
5. Add aggregation and coverage tests.
6. Rescore Mathematics, FinQA and ConvFinQA from saved artifacts.
7. Regenerate multi-step result tables with metric-specific sample counts.
8. Consider final-response generation for FinRetrieval later as a separate protocol.
Final conclusion
The model runs are not the problem. The evaluator is comparing incompatible representations and publishing those comparisons as valid accuracy measurements.
- Mathematics: definite structured-matcher defect.
- FinQA and ConvFinQA: definite formatting and percentage-scaling defects mixed with genuine model errors.
- FinRetrieval: the evaluator never generates the kind of natural-language answer that the benchmark expects.
- Coding and Enterprise groups: correctly have no workflow-final-answer metric.
The narrow baseline repair is to introduce explicit benchmark-specific answer contracts, rescore the recoverable datasets, and leave FinRetrieval workflow-final accuracy unavailable while retaining its valid retrieval and step-level results.
